# C9 as proved: the fast decoder against `Spec.decode`

Plan.md §4 C9 asks for: "End to end, `decode = Spec.decode` (exact for reversible paths;
within C8's bound for irreversible ones)." This note gives the exact statement that is proved,
in plain language, with every side condition and where it comes from. It is meant for the
human to decide whether this is the final form of C9 (task 7.1e; ledger Decision 7.1a).

## The theorem

```lean
theorem JPEG2000.Spec.C9.c9 : ∀ (L : Limits) (data : ByteArray) (reduce : Nat),
    Spec.Equiv.ERel Spec.Equiv.C9Rel (JPEG2000.decodeCodestreamNarrow L data reduce)
      (Spec.Decode.decode L data reduce)
```

`Spec/C9.lean`. It has no hypotheses: `c9 := Spec.Tier2WF.c9_of_hdr Spec.HeaderWF.headerWF`.
`#print axioms` gives `propext`, `Classical.choice`, `Quot.sound` only.

**Scope.** The fast side is `decodeCodestreamNarrow`: one `Int32` plane per component on its own
grid, at reduction `reduce`. It does not cover the consumer API `JPEG2000.decode` (JP2 colour,
palettes, interleaving: Phase 6), which is not part of C9. Both sides call the same
`Header.parse`. The spec has no second header parser; the marker round-trip theorems cover
headers. Both sides also share the output geometry, the `Limits` checks and the tile and
`PPM` iteration.

The ordinary `decodeCodestream` selects this path when all SIZ intervals fit Int32.
`Spec.CodestreamDispatch.compact_c9` transports the theorem through its exact integer
accessor. For a mixed-depth header, `native_geometry` proves the reduced output layout
and budgets, and `native_read` gives each public sample from the sequence of centred
post-MCT tile sources and the G.1 rule. Extending the pre-DC reconstruction to wider
coefficients and transform intermediates is task 7.1k3. Full numerical C9 and the
decoder-side C10 round trip depend on that integration.

**What the spec is.** `Spec.Decode.decode` runs these stages:

* Tier-2: B.10 over un-stuffed bit lists.
* Tier-1: Annex D, all code-block styles, with exact unbounded magnitudes.
* Dequantisation: E.1.1.2, exact over `Int` for 5/3 and `Rat` for 9/7, with the ROI unshift
  of Annex H.
* Inverse DWT: F.3.1, over `Int` for 5/3 and over `Rat` with the T.800 Table F.4 constants
  as exact rationals for 9/7.
* RCT over `Int`, ICT over `Rat`.
* For irreversible samples, rounding half up. Then the DC shift and the clamp of G.1.

## What `ERel C9Rel fast spec` says

### Failures

| fast | spec | allowed? |
|---|---|---|
| error (any) | error (any) | yes (the errors need not be equal) |
| `unsupported` error | success | **yes** (the "unsupported allowance") |
| any other error | success | no |
| success | error | **no** |
| success | success | `C9Rel` must hold (below) |

So whenever the fast decoder returns an image, the spec returns one too, and the two are
related as below. The fast decoder never refuses a stream that the spec accepts, except with
`unsupported`.

**When the allowance is used.** The theorem allows any `unsupported` error. I read the code
to find which ones can actually happen when the spec succeeds. This list is an inspection,
not a theorem:

1. **Tier-1: more than 31 coded bit-planes.** `Tier1.decodeCodeBlock` and
   `decodeCodeBlockSegs` return an `Int32` plane. They refuse a code-block with
   `K = Mb + roiShift − zbp > 31`, where `Mb = G + εb − 1` (E-2). The spec decodes it over
   `Int`. `Spec.Tier1EquivM.c3_all_unsup` proves the fast decoder is `unsupported`
   **exactly** in that case.
   * This is reachable by valid streams: `G ≤ 7`, `εb ≤ 31`, and an ROI shift can be
     large. Examples are a 16-bit lossless stream with `G = 3` and `εb = 30`, or any stream
     with a big `SPrgn`.
   * Common encoder settings (`G ≤ 2`, `εb ≈ depth + gain`, depth ≤ 16, no ROI) give
     `K ≤ 20`.
2. **DC shift: component range wider than `Int32`.** `MCT.DcShift.make` is `unsupported`
   for unsigned depth ≥ 32 or signed depth ≥ 33. `SIZ` allows depths up to 38. The spec's
   DC step never fails.

`reduce > NL` gives `unsupported` on **both** sides, because the skeletons share it, so it
does not use the allowance. Part 2 features, HT code-blocks, and `unsupported` errors raised
while parsing come from the shared `Header.parse` and also fail on both sides.

### Successes: `C9Rel img si`

Unconditionally:

* the same `Header`;
* the same number of components;
* per component, the same `x0`, `y0`, `width`, `height`, depth, signedness, `dx` and `dy`;
* the fast plane has the component's size.

The **sample relation** holds for every sample of every component **only when
`img.saturatedBlocks = 0`**. For a sample `v` (fast) and `x` (spec), `SampleRel` says:
when C8's range precondition `InRangeT` holds for that sample,

* **reversible (5/3) component:** `v = x.value`, so the final samples are **equal**;
* **irreversible (9/7) component:** `|v − x.value| ≤ cellErr(F, mct, levels) + 1`.

Here `x.value` is the spec's final integer sample (exact rational value, rounded half up,
DC-shifted, clamped). The irreversible bound uses these terms:

* `F = fracBitsOf`: `26 − depth` (natural subtraction); under the ICT, the depth is the
  largest of components 0–2.
* `errOf F l = (En(l, 1/2) + 1/2) / 2^F`, where `En` is the multi-level 9/7 error
  propagation of C8 (`DWT97.En`, `E1` applied twice per level, rows then columns). Its
  three terms are:
  * a dequantisation error of `1/2` ulp;
  * the `1/2` ulp of the exact-rounded fallback;
  * the division by `2^F` that converts to sample units.
* Without MCT, `cellErr = errOf F NL`.
* With the ICT, `cellErr = 2.772 · max over components 0–2 of errOf F NL_i + (5/2) / 2^F`.
  2.772 is the largest absolute row sum of the inverse ICT, and `5/2` ulp is the rounding of
  the 30-bit ICT constants (`MCT.ict_c8`).
* The `+ 1` covers the two final roundings: fixed-point `roundFix` against exact
  `roundHalf`.

Computed values of the bound (`errOf + 1` without MCT, `cellErr + 1` with the ICT, the
three components at the same `NL`):

| depth | NL | no MCT | ICT |
|---|---|---|---|
| 8 | 3 | 1.004 | 1.012 |
| 8 | 5 | 1.102 | 1.282 |
| 8 | 8 | 11.9 | 31.2 |
| 8 | 10 | 246 | 681 |
| 12 | 5 | 2.63 | 5.53 |
| 16 | 3 | 2.15 | 4.20 |
| 16 | 5 | 27.1 | 73.4 |

* For the usual 8-bit, `NL ≤ 5` case the bound says the fast sample is within ±1 of the
  spec sample.
* `En` grows about 4.75× per level and `2^F` shrinks with depth. The proved bound is
  therefore weak for 16-bit and for many levels. It is C8's bound as proved, not the
  observed error, which the conformance tests show to be ≤ 1.

### Side condition `saturatedBlocks = 0`

The fast dequantisation narrows to `Int32` with explicit saturation (`Quant.satSigned`) and
counts the code-blocks where that happened. The spec is exact. `C9Rel` asserts nothing about
samples once a saturation occurred, **anywhere in the image**: the condition is global, not
per component.

**Can it be discharged for valid streams within `Limits`?** No, not in general. The argument
below is not machine-checked.

* **Reversible bands, with `K ≤ 31`: no saturation.** Tier-1 magnitudes are `< 2^K ≤ 2^31`,
  and they are multiples of `2^lsb`: only planes ≥ the last decoded plane are set. After the
  ROI unshift, `m' + ⌊2^lsb'/2⌋ ≤ 2^31 − 2^lsb' + 2^(lsb'−1) < 2^31`.
  * To turn this into a theorem, one would need a Tier-1 lemma saying that bits below
    `lsbPlane` are zero, plus a bound on `revCoeff`.
  * `Quant.lean`'s module doc states a weaker bound (`< 2^31 + 2^30`), with no saturation
    for `Mb ≤ 30`.
* **Irreversible bands: saturation is reachable by valid streams.** The fixed-point value
  is `(2·mag + 2^lsb)·(2^11 + μb)·2^(Rb + F − εb − 12)`, with `mag < 2^Mb`,
  `Mb = G + εb − 1` and `Rb = depth + gb`. Here `gb = 0` for LL, 1 for HL and LH, and 2 for
  HH. For `depth ≤ 26`, `F = 26 − depth` and the value is `< 2^(G + gb + 26)`. So:
  * **no saturation if `G + gb ≤ 4`**. `G ≤ 2` is enough for every band, and the common
    encoder defaults are `G ∈ {1, 2}`;
  * **counterexample**: an 8-bit 9/7 stream with `G = 7` and `εb = 8` in an HH band, so
    `Mb = 14` and `K = 14 ≤ 31`. One code-block codes all 14 planes with magnitude
    `2^14 − 1`. Its fixed-point value is about `2^34`, so it saturates.
    * The stream is syntactically valid T.800 and fits any `Limits` that admit a tiny image.
    * Nothing in T.800 requires the coefficients to come from an image in range.
  * For depth > 26, `F = 0` and the value is `< 2^(G + gb + depth)`. Saturation is then
    reachable with small `G`.

So `saturatedBlocks = 0` can only be discharged under extra conditions on the header:

* reversible only;
* or irreversible with `depth ≤ 26` and `G + 2 ≤ 4`.

It cannot be discharged for all valid streams. Removing it would need a different fast
design, for example an `Int64` or exact fallback for saturated blocks.

### Side condition `InRangeT` (C8's "no overflow")

`InRangeT` is checked per sample, on the spec's trace (`x.peers`: the exact inverse-DWT
outputs the sample is computed from).

* **Reversible without MCT:** vacuous. The sample relation is unconditional, given
  `saturatedBlocks = 0`.
  * The fast 5/3 recomputes exactly on overflow and saturates (`DWT53PlaneEquiv`: the
    output is `clamp32` of the exact value).
  * The G.1 clamp to the sample range then gives the spec's sample.
* **Reversible with RCT:** the three exact 5/3 outputs must lie in `Int32`. Otherwise the
  fast RCT works on clamped values and the spec's does not.
* **Irreversible:** `2^F ·` each exact 9/7 output must lie in `Int32`.

**Can it be discharged for valid streams?** No, not syntactically. The argument is not
machine-checked.

* **Counterexample (reversible, RCT, no saturation):** a 5/3 band with `G = 2` and
  `εb = 30`, so `K = 31`.
  * A low-pass coefficient is `2^31 − 1` and its high-pass neighbours are `−(2^31 − 1)`. These
    dequantise without saturation.
  * The lifting step `x_even = s − ⌊(d + d' + 2)/4⌋` then gives about `2^31 + 2^30`, outside
    `Int32`.
* **Streams encoded from an actual image:**
  * Lossless: the exact 5/3 outputs are the image's RCT components, so they are in range
    for depth ≤ 29.
  * Lossy: the exact 9/7 outputs are the image plus the quantisation error, about
    `2^depth · 2^F = 2^26 ≪ 2^31`.
  * In both cases `InRangeT` holds. But "came from an image" is a property of the encoder,
    not of the codestream. The decoder cannot check it, and a theorem would have to assume
    it.

### Summary for reviewers

| path | what C9 gives | extra conditions |
|---|---|---|
| reversible, no MCT | **equal samples** | `saturatedBlocks = 0`; no saturation is possible for these blocks when `K ≤ 31` (informal argument above), but the condition is image-global |
| reversible + RCT | equal samples | also `InRangeT` on the three 5/3 outputs |
| irreversible (± ICT) | `|fast − spec| ≤ cellErr + 1` (table above) | `saturatedBlocks = 0` and `InRangeT` |
| any | fast fails only where the spec fails, or with `unsupported` (K > 31; depth ≥ 32/33) | — |

Plan §4 says "exact for reversible paths; within C8's bound for irreversible ones". The
proved statement matches that wording. It adds three things:

1. the `unsupported` allowance;
2. the global `saturatedBlocks = 0` premise;
3. the per-sample `InRangeT` premise.

Each of the three can be triggered by syntactically valid streams within `Limits` (the
counterexamples above). None of them can be triggered by the coefficients an encoder
produces from an in-range image with common settings (`G ≤ 2`, depth ≤ 26, `K ≤ 31`).
These three are the human's decision:

* whether this is the final form;
* or whether C9 should be restated under a named, checkable precondition on the header
  (such as the `G + gb ≤ 4`, `depth ≤ 26`, `K ≤ 31` conditions above), which would discharge
  `saturatedBlocks = 0` but not `InRangeT`;
* or whether the fast decoder should change, for example to exact fallbacks through the
  MCT and for saturated blocks.

## The proofs C9 depends on

`Spec.C9.c9` unfolds to this chain. Each name is a theorem in the repository.

* `Spec.HeaderWF.headerWF` (`Spec/HeaderWF.lean`, task 7.1e) proves `HeaderWF`:
  * every tile-component's step mantissas are `< 2^11`, because `readStepSize` masks with
    `0x7FF`. The proof goes through `readQuant`, the main-header and tile-part loops,
    `bandSteps`, `mkComp`, `mainCoding`, `tileCoding` and `Layout.ofHeader`;
  * components 0–2 have equal transforms under the MCT (`checkMct`).
* `Spec.Tier2WF.c9_of_hdr` (task 7.1g) is `Spec.Tier1Wire.c9_of_header Spec.Tier2WF.tier2WF`.
  * `Spec.Tier2WF.tier2WF` proves `Tier2WF`: band labels and code-block rectangles are
    consistent with the layout, and segment ranges lie inside the input.
* `Spec.Tier1Wire.c9_of_header` (task 7.1h) is `Spec.Tier2Wire.c9_of_open` with
  `Spec.Tier1Wire.tier1Equiv`.
  * That comes from `Spec.Tier1EquivM.c3_all_unsup`, which is C3 for every code-block style
    with fast `unsupported` exactly when K > 31.
  * `c3_all_unsup` is built on `Spec.Tier1EquivM.c3_all` and the plain-mode
    `Spec.Tier1Equiv.c3_plain`.
* `Spec.Tier2Wire.c9_of_open` (task 7.1f) is `Spec.Equiv.c9_of_stages` with these
  theorems:
  * `Spec.Tier2Wire.tier2Equiv`, from `Spec.Tier2Equiv.tier2_equiv_of_siz` (7.1b) and
    `Spec.Equiv.parse_dxdy`;
  * `Spec.QuantBlock.dequantLoopEquiv` (7.1d), built on the kernels `Quant.revCoeff_eq` and
    `Quant.irrevCoeff_bound`;
  * `Spec.DWTPlane.dwt53PlaneEquiv` (7.1d), built on `DWT53.lift1d_eq_sr1d`;
  * `Spec.DWTPlane.dwt97PlaneErr` (7.1d), built on C8's `DWT97.qsrMulti_err`.
* `Spec.Equiv.c9_of_stages` (task 7.1a) composes these, which are proved outright in
  `Spec/Equiv.lean`:
  * `tile_rel`, `tileComp_rel` and `fin_rel`;
  * `mct_step`, from `MCT.rctSample_eq`, `MCT.ictSample_eq`, `MCT.ict_c8` and
    `MCT.map3_get`;
  * `dc_step`, from `MCT.DcShift.rev_eq`/`irrev_eq`, `MCT.reconIrrev_sat` and
    `Spec.MCT.roundFix_err`;
  * `placeEquiv`;
  * the skeleton identities `decodeCodestream_eq_with`, `decodeTile_eq_with` and
    `reconstructTileComp_eq_with`, which hold by `rfl`. Any edit to the three fast
    functions must keep these in step.
